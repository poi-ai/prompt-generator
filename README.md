CUIでいくつかの質問に答えるだけで、生成AIに投げるプロンプトを作る静的ジェネレータ。

質問への回答を機械的にテンプレートへ流し込むだけで、生成AIは介在しません。

**[Claude Code](https://claude.com/claude-code) への入力を主な用途として想定しています。** サブエージェント・フェーズ分けの質問や、`claude/` から始まる自動生成ブランチの扱いに関する指示など、生成されるプロンプトの内容の一部はClaude Code固有の概念を前提にしています。他のツールに投げても動作はしますが、その場合はプロンプト中のこれらの記述を読み替えるか、適宜編集してください。

## 特徴

- **計画立案・直接実行の両方に対応**
  「実装して」「レビューして」と直接依頼する**直接実行**用のプロンプトだけでなく、まず**計画(作業手順)を立てさせる**プロンプトも生成できます。単発の簡単な作業は直接実行、規模の大きい作業は計画立案から、と使い分けられます。
- **回答をそのまま出さず、意図の伝わる説明文にする**
  質問への回答を`## 質問\n回答`という機械的な羅列にはせず、「下記の観点を重点的に確認すること」のような説明文の中に埋め込みます。背景や意図も文章で添えるため、AIが計画を立てる際に意図を汲み取りやすくなります。
- **作業完了後に投げるフィードバック依頼プロンプトも生成する**
  メインのプロンプトとは別に、「元の指示文のどこが曖昧・不足していたか」をAIに振り返ってもらうためのプロンプトも一緒に生成します。フィードバックを本題のプロンプトに混ぜないことで、計画立案の精度を落とさずに改善点を集められます。
- **矢印キーで選択できる**
  選択式の質問は↑↓キーで選び、Enterで決定します。複数選択の質問はSpaceで選択/解除します。
- **誤入力に気づいたら前の質問に戻れる**
  回答を確定して次の質問に進んだ後でも、1つ前の質問に戻ってやり直せます。誤って違う選択肢を選んだ・入力を間違えた場合に、最初からやり直す必要はありません。
- **外部ライブラリ不要**
  Python標準ライブラリのみで動作します(矢印キー入力にはWindows標準の`msvcrt`を使用)。

## 動作環境

- Windows + Python 3.10以降
- 追加パッケージのインストールは不要

Windows以外の環境では矢印キーの代わりに番号入力へ自動的にフォールバックします(開発・動作確認用)。

## 使い方

`run.bat` をダブルクリックすると起動します。

コマンドラインから直接実行する場合:

```
python main.py
```

起動後は質問に順番に答えていくだけで、最後に生成されたプロンプトが出力されます。

## 生成できるプロンプトの種類

| ジャンル | 内容 | 種別 |
| --- | --- | --- |
| コーディング | 実装を行わせる(計画立案 / 直接実行) | 新規機能実装 / 改修 / バグ修正 |
| コード調査 | 調査を行わせる(計画立案 / 直接実行) | 原因調査 / 影響範囲調査 / 仕様・実装の理解 |
| コードレビュー | レビューを行わせる(計画立案 / 直接実行) | ファイル・ディレクトリ指定 / PR・コミットハッシュ指定 |
| 設計書作成 | 設計書作成を行わせる(計画立案 / 直接実行) | 新規作成 / 既存更新 |
| 設計書レビュー | 設計書レビューを行わせる(計画立案 / 直接実行) | ファイル指定 / PR・コミットハッシュ指定 |
| Issue作成 | GitHub Issueを作成させる(**直接実行のみ**) | バグ報告 / 機能要望 / 変更要望 |

## 質問の流れ

```
1. 計画立案 / 直接実行の選択
2. ジャンル選択
     └ 直接実行を選んだ場合のみ、選択肢の先頭に「Issue作成」が追加される
3. 対象システムのディレクトリ選択
     └ 作業環境(ローカル/リモート)を選択したうえでディレクトリを入力する。ローカルは裏で直下の .git の有無を判定し、リモートはgitリポジトリかどうかを直接質問する(パスの実在チェックは行わない)
4. 種別選択 → 種別ごとの追加質問(本題)
5. ジャンル共通の質問(目的・出力形式・制約条件など)
6. サブエージェント・フェーズ分けの方針(全ジャンル共通)
7. GitHub Issue関連 ※gitリポジトリの場合のみ
     ├ コーディング / 設計書作成  … Issue・ブランチ・コミット規約・PR作成まで質問
     └ その他3ジャンル            … Issueの有無と結果の記録可否のみ質問
8. 出力先選択(ターミナル表示 / mdファイル出力 / 両方)
```

本題(何をしてほしいか)を先に、Git/GitHub関連の運用ルールを後に聞く順番にしています。

### 前の質問に戻る操作について

質問への回答を誤って入力・選択したまま次の質問に進んでしまった場合、1つ前の質問まで戻ってやり直せます。何度も戻り操作を行えば、その分だけ前の質問まで遡れます(計画立案/直接実行の選択より前には戻れません)。

| 質問の種類 | 戻る操作 |
| --- | --- |
| 選択式(矢印キーモード) | Backspaceキー |
| 選択式(番号入力モード) | `b` を入力してEnter |
| 自由入力(テキスト入力) | `:b` のみを入力してEnter |

種別選択(新規機能実装/改修/バグ修正など)の直後にある個別質問で戻ると、その種別選択自体からやり直しになります。出力先選択(ターミナル表示 / mdファイル出力 / 両方)は質問フローの最後にあるため戻る操作の対象外です。

### 計画立案 / 直接実行について

ジャンル選択より前に、生成するプロンプトを「計画立案(まず作業計画を立てさせる)」「直接実行(その場で作業を行わせる)」のどちらにするか選びます。

- **計画立案**: 「実装計画を立ててください。この時点では実際の実装は行わないでください」のように、まず作業手順を立てさせるプロンプトになります。規模の大きい作業や、事前にすり合わせを挟みたい場合向けです。
- **直接実行**: 「以下を実装してください」のように、その場で作業そのものを行わせるプロンプトになります。単発の簡単な作業で、わざわざ計画を立てさせる必要がない場合向けです。

いずれのモードでも、対象・目的・出力形式・制約条件などの質問内容自体は変わりません。生成されるプロンプトの冒頭の依頼文と、作業内容セクションの文言だけがモードに応じて切り替わります。

### 「Issue作成」ジャンルについて

直接実行モードでのみ選べる、GitHub Issueをその場で作成させるためのジャンルです。単発の軽い作業であり計画を立てさせる意味がないため、計画立案モードの選択肢には出てきません。

種別(バグ報告 / 機能要望 / 変更要望)ごとの質問は、コーディングジャンルの「バグ修正」「新規機能実装」「改修」で使っている質問(現象・再現手順・期待する動作など)をそのまま流用しています。対象ディレクトリ選択も他ジャンルと共通です。単発の作業のため、サブエージェント・フェーズ分けの質問やGitHub Issue/PR関連の質問(次項)は出ません。

### Issueについて

Issue番号は1つの数値入力にまとめています。

- `0` … 新規にIssueを作成する
- `-1` … Issueを使わない
- 正の数 … その番号の既存Issueを使う

新規作成時はGitHub側が採番するまで実際の番号が分からないため、「作成したIssueの番号を使ってブランチを作成すること」のように**番号を決め打ちしない指示**になります。既存Issueを指定した場合のみ、その番号を使ったブランチ名・コミットメッセージの指示が具体的に出力されます。

既存Issueを指定した場合、`gh issue view <番号>` を実行してIssueの内容を確認するよう指示しますが、実行できない・失敗した場合は推測で進めずユーザーに確認するよう指示する一文もあわせて出力されます。

Issueを使うかどうかに関わらず、続けて「コミット・プッシュしますか?(両方行う / コミットのみ行う / どちらも行わない)」を必ず質問します。「どちらも行わない」を選んだ場合を除き、コミットメッセージの規約(Issueを使う場合のみ)とあわせてコミット・プッシュに関する指示が出力されます。PRの作成可否は「コミット・プッシュ両方行う」を選び、かつIssueを使う場合のみ質問されます(プッシュしない場合はPRを作成できないため)。

### サブエージェント・フェーズ分けについて

規模の大きい作業でコンテキスト長が伸び、精度が落ちたりトークン制限に到達したりするのを防ぐための質問です。

- **サブエージェントの累計起動数の上限**: 数値で1問に統合(`0`を入力すると「活用しない」を意味します。あくまで累計の上限で、同時起動数の上限ではありません)
- **ファクトチェック・ダブルチェックの実施可否**: 最大起動数が**2以上**の場合のみ追加で質問されます(担当箇所ごとに独立2体で突き合わせるにはサブエージェントが最低2体必要なため)
- **完了報告のタイミング**: 最大起動数が**2以上**の場合のみ追加で質問されます。「1体完了するごとに報告させる」「すべて完了してから一括で報告させる」の2択です
- **フェーズ分け**: 区切りで一旦立ち止まる / 区切りでの確認は不要 / 分割せず一気に進める

いずれも選択肢をそのまま出力せず、「メインエージェントのコンテキスト長が伸びることで精度が下がるのを防ぐため〜」のように意図を説明する文章としてプロンプトに埋め込まれます。

ファクトチェック・ダブルチェックを「行う」を選んだ場合、実装・調査を行うすべての担当箇所を独立した2体のサブエージェントに担当させて結果を突き合わせるよう指示する文言が追加されます。突き合わせで内容の不一致・矛盾が見つかった場合は、さらに第三者の検証用サブエージェントを追加起動して裏取りさせる指示も含まれます。「行わない」を選んだ場合や、最大起動数が1体の場合はこれらの指示は追加されません。

完了報告のタイミングで「すべて完了してから一括で報告させる」を選んだ場合、個々のサブエージェントが完了するたびに逐次報告せず、全体の完了を待って結果をまとめて一括報告するよう指示する一文が追加されます。サブエージェントごとに完了通知が来ることが多く、デスクトップアプリ版では通知が都度飛ぶ・最終結果がまとまった形で見えない、といった点が気になる場合に選んでください。「1体完了するごとに報告させる」を選んだ場合はこの指示は追加されません(既定の挙動のまま)。

サブエージェントを活用する場合は、対象の規模に対して起動数やフェーズ分割が過剰だと判断したら独断で減らさずユーザーに確認を取ること、という一文も常に追加されます。

また、**コーディングジャンルに限り**、最大起動数が2以上の場合、複数のサブエージェントが同一ファイルを同時に編集することがないよう、担当ファイル・担当範囲が重複しないようタスクを割り振ることを指示する一文が追加されます(コード編集を伴わない調査・レビュー・設計書系のジャンルでは、この指示はノイズになるため出力されません)。

### フィードバック依頼プロンプトについて

メインのプロンプトが生成されると、あわせて「作業完了後に投げるフィードバック依頼プロンプト」も生成されます。中身は、メインのプロンプト全文を引用(`>`)としてそのまま埋め込んだ上で、「推測・仮定して進めた箇所はあったか」「曖昧だった箇所はあったか」など、**指示文自体**への率直な意見を求める内容です。作業内容そのものへの評価ではありません。

会話の途中でセッションを切り替えるケースを考慮し、「先ほどの指示文」のような会話上の位置に頼った参照はせず、指示文の全文を埋め込むことで、どのタイミング・どのセッションでフィードバックを求めても参照先が一意になるようにしています。

## 生成物の保存先

| パス | 内容 |
| --- | --- |
| `output/<ファイル名>.md` | 生成したプロンプト(mdファイル出力を選んだ場合) |
| `output/<ファイル名>-feedback.md` | フィードバック依頼プロンプト(mdファイル出力を選んだ場合) |
| `history/directories.txt` | 過去に入力したディレクトリの履歴(最大10件) |

どちらも実行時に自動で作成されるため、事前準備は不要です。ローカル環境固有のデータなので`.gitignore`で除外しています。

ディレクトリの履歴は次回以降の実行時に選択肢として表示されます。存在しなくなったディレクトリは選択肢と履歴ファイルの両方から自動的に削除されます。リモート環境を選んだ場合に入力したパスは履歴に保存されません。

## ファイル構成

```
main.py                 エントリポイント(モード選択・ジャンル選択・出力先選択)
menu.py                 矢印キーによる選択メニュー(単一選択・複数選択)・自由入力の共通ヘルパー
wizard.py               前の質問に戻れる質問フローの共通ヘルパー
directory.py            対象ディレクトリの選択(履歴・存在チェック・gitリポジトリ判定)
github.py               GitHub Issue/PR関連の質問
execution_strategy.py   サブエージェント・フェーズ分けの質問(全ジャンル共通)
feedback.py              フィードバック依頼プロンプトの組み立て(全ジャンル共通)
genres/
  coding.py             コーディング
  investigation.py      コード調査
  review.py             コードレビュー
  design_doc.py         設計書作成
  design_review.py      設計書レビュー
  issue.py              Issue作成(直接実行のみ、coding.pyの質問を流用)
run.bat                 Windows用の起動スクリプト
```

ジャンルや種別は「ラベルと処理関数の対応表」から呼び出す構成にしているため、条件分岐を増やさずに追加できます。
