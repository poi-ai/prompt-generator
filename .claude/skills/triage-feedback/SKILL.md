# AIフィードバックの仕分けと反映

このリポジトリの `feedback.py` は、このジェネレーターが作ったプロンプトを別セッションで実行した後、**元の指示文そのもの**への振り返りを求める「フィードバック依頼プロンプト」を生成する。ユーザーはそのAIからの回答を、このSkillの引数としてそのまま貼り付ける。やるべきことは、それを実際にこのジェネレーターへの改善につなげるか、対象外として説明するかの判断である。

## なぜ全部そのまま直さず仕分けるのか

貼られたフィードバックは、あくまである1回の実行についての振り返りである。その中には、このジェネレーターの質問内容・生成される文言・CLAUDE.mdのルールに実際に反映すべきものもあれば、実行先のリポジトリ固有の事情だったり、単発の事情だったり、すでにこのジェネレーターが質問済みの内容と重複していたりして、ここでは対応しようがないものも混ざっている。中身を吟味せずに全部反映しようとすると、的外れな対応や思い込みでコードを増やすことになる。だからこそ、コードを書く前にまず仕分けてユーザーに確認する。

## 手順

1. **フィードバックを1点ずつ読む。** それぞれについて次のどちらかを判断する。
   - **対応候補**: このジェネレーターの質問・生成される文言・`CLAUDE.md`のルールを直せば防げた、または解消できた内容
   - **対応不要**: 実行先のリポジトリ・コードそのものへの指摘、単発の事情、抽象的すぎて具体的な変更に落とし込めないもの、既にこのジェネレーターが質問・出力済みの内容と重複するもの

2. **コードを書く前に、両方のリストを提示する。** 「対応候補」はそれぞれ、どのファイル・どの質問・どの文言をどう変えるつもりかを一言添える(この時点ではまだ実装しない)。「対応不要」にはそれぞれ理由を一言添える。ここでユーザーが仕分けの読み違いを訂正できるようにする。

3. **承認を待つ。** 全部承認される場合もあれば、一部だけ・方針の修正を挟んで承認される場合もある。ユーザーの判断に従う。

4. **承認された分だけ `CLAUDE.md` の手順に従って実装する。** ブランチ・Issue・コミット・コメントに関するルールは `CLAUDE.md`(プロジェクト指示として既に読み込まれている)に従い、ここでは繰り返さない。要点は、関連する承認済みの対応候補をまとめて1つのGitHub Issueにしてよいこと(関連が薄いものが混ざっている場合は、別Issueに分けるかどうかを先にユーザーに確認する)、`#<Issue番号>` ブランチを作ること、実装後は必ず動作確認すること(このツールはテストスイートを持たない対話型CLIのため、`menu.select`/`menu.ask_text` をモックした簡易スクリプトで対象の関数を直接呼び出し、実際の出力を確認する)、commit・pushまで行うこと。マージはしない。pushしたら完了を報告し、マージするかどうかはユーザーの明示的な指示を待つ。

5. **対応しなかった点についても報告する。** 「対応不要」とした指摘も、見落としではなく意図的に対象外としたことが伝わるよう、理由とあわせて簡潔に報告する。
