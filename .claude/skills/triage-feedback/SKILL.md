# Triage AI feedback into fixes

This repository's `feedback.py` generates a「フィードバック依頼プロンプト」that another AI session fills out after finishing work generated by this tool, reflecting on the ORIGINAL INSTRUCTION TEXT itself (not the work it did). The user pastes that AI's answer here as this skill's argument. Your job is to turn it into concrete improvements to this generator - or explain why a point doesn't apply.

## Why triage instead of just fixing everything

The pasted feedback is about one specific run of one specific prompt. Some of it is genuinely a gap in how this generator asks questions or phrases output - worth fixing. Some of it is about the target repository's own code, a one-off circumstance, or already covered by a question this generator asks - not actionable here. Acting on all of it unfiltered would inflate this codebase with responses to noise or misdiagnoses. That's why this skill sorts and asks before writing any code.

## Steps

1. **Read the feedback point by point.** For each point raised, decide:
   - **Fixable here**: something in this generator's questions, generated wording, or `CLAUDE.md` rules would have prevented or addressed it.
   - **Not applicable**: specific to the target repo/code that was worked on, a one-off, too vague to act on, or already covered by an existing question/instruction this generator produces.

2. **Present both lists before writing any code.** For each "fixable here" item, give a one-line idea of what would change (which file/question/wording) - not a full implementation yet. For each "not applicable" item, give a short reason why. This is the point where the user corrects your read of the feedback if you got it wrong.

3. **Wait for approval.** The user may approve everything, a subset, or push back on your proposed approach for an item - follow whatever they land on.

4. **Implement approved items following `CLAUDE.md`.** This repo's `CLAUDE.md` (already loaded as project instructions) defines the branch/Issue/commit/comment rules - follow it rather than improvising. In short: one GitHub Issue per batch of related approved fixes (if unrelated items were approved together, ask the user whether to split into separate Issues before creating them), a `#<Issue番号>` branch, implement, verify the change actually does what it should (this is an interactive CLI with no test suite - verify by monkeypatching `menu.select`/`menu.ask_text` in a throwaway script and calling the affected function directly, then check the output text), commit, push. Do not merge - after pushing, report and wait for the user to say so explicitly.

5. **Report on what you skipped, not just what you did.** Even for "not applicable" items, restate briefly why, so the user isn't left wondering whether they were missed rather than deliberately excluded.
